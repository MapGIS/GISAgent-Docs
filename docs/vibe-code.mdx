# 氛围编程（Vibe Code）

> 氛围编程的标准循环是  说清需求 => 选对模式（Plan 规划 / Build 执行）=> AI 生成 => 预览检验 => 精准反馈 => AI 修复，循环推进
> 成败的关键在反馈质量——同一句"加载失败"，给 F12 报错原文的三轮修好，只说"看不见图"的修五遍也没动

不会写提示词也能做出能跑的应用，这是氛围编程（vibe code）的门槛；但要从"能跑"走到"能交付"，靠的是下面这几条反馈纪律。

另一个常见卡点是**模式没选对**：在 Plan（规划）模式下，AI 只能读、不能写，再催也不会动文件。先认清两种模式，比反复换提示词有效得多。

## 一、反馈的三条纪律

### 1. 报错给原文，不给感受

"看不见图""做的很乱"这类自然语言，AI 无法精准定位；**F12 的错误日志，AI 基本一把过**。反馈时带上报错原文 + 文件行号 + 触发操作（具体模板见[预览排障](/docs/preview-error)）。

配套纪律：**删对话 = 删现场**。有用户反复改不好就"把这个对话删了重新发起"——新对话里 AI 看不到之前生成的代码和改过 5 遍的历史，反而更定位不了，而且删掉的内容连技术支持也找不回来。**不需要删，AI 可以在原对话里自修复**。

### 2. 渐进式、结果驱动，一步一验收

不要一句话要 10 个页面 + 全部交互 + 完美 UI。正确节奏是先让 AI **把地图和管网搞出来**，跑通后再逐层加页面、调细节——每步都有可验收的结果，错了知道错在哪一步。第一轮就要大而全，结果往往是"看着都有、处处是坑"，返工成本远高于渐进式。

### 3. 提示词不行，先让 AI 帮你写提示词

不会写提示词没关系：**把需求先发给 DeepSeek，让它生成结构化提示词，再复制给工作平台的 AI**。把两份回答放在一起对比，反复临摹几次，就摸清了 AI 的"性格"和对话方式——这比背提示词模板有效得多。

## 二、两种模式：Plan（规划）与 Build（执行）

> 同一个对话框，Agent 可能处于两种模式。**模式决定它"能不能写文件"**，不是模型能力差异，也不是 AI 偷懒。

快速判断：输入框旁的模式胶囊显示 `Plan`（或 规划/Architect）= 只读；显示 `Build`（或 执行/Code/Auto）= 可写。

GIS Agent 接入的编码 Agent（如 OpenCode）通常会把模式归为两类：

| 维度 | Plan（规划） | Build（执行） |
| :--- | :----------- | :------------ |
| 常见叫法 | 规划 / Architect / Ask（不同 Agent 叫法不同） | 执行 / 构建 / Code / Auto / Execute |
| 读文件、搜索、分析 | 可以 | 可以 |
| 写文件、改代码、系统变更 | **不可以（只读）** | **可以** |
| 典型输出 | 方案、步骤、风险、改动清单 | 代码、文件、命令、预览 |
| 适合 | 需求澄清、架构设计、影响面分析、评审 | 方案已确认、落地实现、修 bug |
| 风险 | 低（不动现场） | 中高（会改文件，需要验收） |

### 2.1 为什么会卡在"规划模式"

用户常遇到这样的回复：

> 系统当前仍明确处于规划模式（只读阶段）……禁止我进行任何文件写入或系统变更……请在客户端界面中将当前模式从 Plan 切换为可执行模式。

这不是 AI 拒绝干活，也不是它在"请示"；**Plan 模式在系统层禁用了写入工具，模型无法靠对话指令解除**。你对它说"你可以直接改""我授权你写"，都不会生效——约束在模式层，不在提示词层。

常见触发：

* 新建会话时沿用了上次的 Plan 偏好，或创建时没注意模式；
* 手动把模式切成了 Plan（规划/Architect）；
* 当前是历史会话/只读会话，写入本来就被禁用；
* 该 Agent 只暴露了 Plan 类模式，没有可写模式。

### 2.2 怎么切换（30 秒）

1. **看模式胶囊**：在输入框右下角（新对话页和对话页都有）找到带滑杆图标的按钮，上面显示当前模式名（如 `Plan`）。部分布局在标题栏。
2. **点开选执行模式**：在"模式"菜单里选 `Build`（也可能叫"执行/构建/Code/Auto/Execute"，以你的 Agent 为准）。
3. **回复"继续"**：同一会话内切换即可，上下文、已上传文件、已生成代码通常都还在，不需要重述需求；如果发现上下文丢了，再把计划贴过去。也可以说"按上面的计划执行"。
4. **切不动怎么办**：
   * 按钮是灰的：AI 正在回复，等它停下来再切；
   * 看不到模式胶囊：可能是只读/历史会话，或该 Agent 没有暴露模式；新建会话，在发送前选 Build；
   * 切完仍说 Plan：确认胶囊文字已变成 Build；没变就刷新/重试，仍不行再新开会话并把计划贴过去。

> AI 只能看到对话，看不到你的界面；它建议"切换模式或新开会话"是通用说法。GIS Agent 支持**会话内切换**，优先原地切，切换失败再新开。

**两个容易混淆的概念：**

* **Plan 模式 ≠ 只读会话**：页面出现"仅可查看历史记录"提示、输入框不可用时，是会话级只读（历史会话/Agent 不一致），不是切模式能解决的，需要新建会话。
* **模式是会话级的**：你在 A 会话切到 Build，不会自动改 B 会话；新会话开始前再看一眼模式胶囊，别假设它会继承上次选择。

### 2.3 什么时候用哪个

* **先 Plan 再 Build**：需求还很虚、要动多个文件/数据库、要先看影响面、要做架构或风险评审时，先在 Plan 里只读分析，拿到改动清单和验收标准，再切 Build 执行。
* **直接 Build**：需求明确、改动小、只是改文案/样式/一个函数，直接在 Build 里做，省一轮。
* **推荐循环**：`Plan 只读分析 → 人工确认 → Build 执行 → 预览验收`；大改或回归问题再切回 Plan 分析，确认后继续 Build。

一句话原则：**Plan 用来"想清楚"，Build 用来"做出来"；不要让 Plan 干 Build 的活，也不要在 Build 里边想边大改。**

### 2.4 常见误区

* **"AI 不肯干活"**：先看模式，不要先怀疑模型能力。
* **"我已经说'你可以改'了"**：聊天指令不能覆盖系统模式；必须在界面上切。
* **"Plan 模式也能生成代码"**：它可以在消息里展示代码，但不会落盘；看到代码不等于文件已改。
* **"切换 Build 就一定能写"**：还要看工作区权限、只读会话、工具是否可用；报错就按[预览排障](/docs/preview-error)贴原文。
* **"每次都要先 Plan"**：简单任务直接 Build；复杂任务才值得先规划。
* **"删对话重来"**：删了上下文和现场都没了；先切模式，切不动再新开（呼应第一节的"删对话=删现场"）。
* **"CLI 里按 Tab 能切，网页上也可以"**：不同 Agent 的快捷键只在其 CLI 里有效；Web 端以模式胶囊为准。

### 2.5 可直接复制的两句话

规划阶段：

```text
当前先不要改文件。请只读分析，给我：1) 要改哪些文件/模块；2) 风险和影响面；3) 验收标准。
我确认后再执行。
```

执行阶段：

```text
已切换到 Build 模式，按上面的计划直接改文件并运行验证；
完成后给我改动清单、diff/预览和自检结果。
```

## 三、真实踩坑对照

以下每一条都来自实际的氛围编程现场：

| 现象 | 现场还原 | 正确姿势 |
| :--- | :------- | :------- |
| AI 反复说"当前处于规划模式/只读"，拒绝写文件 | 会话在 Plan（规划）模式；只读是系统级硬约束，聊天里说"你可以改"无法覆盖 | 点输入框旁的模式胶囊 → 切到 Build（执行）→ 回复"继续"；按钮灰色就等回复结束；只读会话则新建会话并在开始前选 Build |
| 底图瓦片全挂，报 `ERR_NAME_NOT_RESOLVED` | 提示词里写了 `https://t{0-7}.tianditu.gov.cn/...`，AI 把 `{0-7}` 原样照抄进代码，浏览器真去解析这个域名 | **直接贴一条能打开的完整 URL**（含真实 x/y/z 和 tk），让 AI 反推模板；报错原文一贴，AI 一轮就改成 t0/t1/t2 具体域名列表 |
| 后台"请求了国外的底图"加载不上 | 页面代码里默认 OSM/国外 CDN，内网环境不可达 | 把 F12 **Network** 标签的失败请求发给 AI，明确要求换国内底图 |
| 底图能出图但数据整体偏移几百米 | 数据与底图坐标系不匹配（WGS84/GCJ02/BD09 混用），不是预览 bug | 按[空间参考系](/docs/spatial-crs)的匹配决策表处理，别在预览问题里绕圈 |
| 页面区块"内容都是空的" | 根因藏在代码里：`height: calc(100vh - 320px)` 算出的容器过矮、`App.initMap` 定义了但模块 `return` 里没导出 | 说清**哪个页面哪个区块**+ 附 Console 报错，两类问题 AI 都能一轮定位；只说"是空的"就要来回猜 |
| 改了 5 遍没修好，删对话重来 | 每轮反馈都是"还是不行"级别的感受描述 | 改不好通常不是 AI 无能，是反馈里缺报错原文；补上日志原话即可续修 |
| 反复横跳：画了过滤又撤销、撤销又重做 | "删除不在 DMA 范围内的点位"→ 两分钟后"撤销"→ 又按边界框重做一遍 | 下指令前**先让 AI 报影响面**（"这个操作会改动哪些文件、影响哪些点位？"），确认后再执行，一个来回就省两轮 |
| 数字明显不合理没人发现 | 成果汇报写"管线总长 17,385 km"——实际整个管网约 167 km，单位换算错了两个量级 | AI 的自报数字要抽查量级：13 平方公里城区管网不可能是上万公里；发现后把该行输出贴回对话让 AI 修单位 |

## 四、需求陈述模板

一条合格的首轮需求包含五件事，缺一件就多一轮往返：

```text
目标：做一个漏损管控专题图，DMA 分区 + 压力监测 + 漏损定位
数据：用本对话上传的"管网数据1016.rar"，不要自己编管网
底图：天地图，用这条地址的格式（贴完整可用 URL，含 tk）
交互：图层开关、点击查看详情、左侧分区列表点击后飞行定位
验收：打开 index.html 能看到管网叠加在天地图底图上、无 Console 红色报错
```

* **数据口径写死**："管网数据采用本对话中上传的文件"这类指认，能避免 AI 用模拟数据顶替真实数据。
* **验收判据写在需求里**：把"能看到什么算做完"提前说清，AI 交付前会自检，你验收也有依据。
* **模式先选对**：这轮是"只读规划"还是"直接执行"，先在输入框旁的模式胶囊里选；提示词里再写一句"先给方案，不要改文件"，能让 AI 明确这一轮只做分析，减少来回确认。
* **tk/token 只留在对话里**：含 token 的 URL 不要写进对外交付的文档、页面或截图。

## 五、过软件工程这道门槛

氛围编程有一个分水岭：**能不能从"自然语言预研"进化到"软件工程"**——需求能拆步、反馈带日志、结果做验收、版本能回退。迈过去，产出就不再是单页面 demo，而是页面之间联动跳转、人机交互完整的系统；迈不过去，就会一直停在"改 5 遍还是不行"的循环里。

判断自己是否已经过线，看三个行为：

1. 反馈里出现的是 `Uncaught TypeError: ... at app.js:147` 而不是"坏了""很乱"；
2. 大需求会主动拆成"先地图管网 → 再十个页面 → 再补空区块"的阶梯；
3. 收到成果会先核一眼数字量级和预览，再进入下一轮。

***

**使用提示：** 每次卡住时先自问——"我把 F12 的原文给 AI 了吗？模式选对了吗？这一步能不能再拆小？"这三个动作能解决氛围编程里八成的挫败。
